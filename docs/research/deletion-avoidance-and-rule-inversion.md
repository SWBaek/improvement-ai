# 삭제 회피와 규칙 반전

- 조사일: 2026-08-13
- 관련 일화: 2026-08-21. 공개 출력 형태는 Idea note의 공개 일화 절, 재현 가능한 프로젝트 산출물은 프로젝트 사례 절. Idea는 대상 잔존(A)과 부재 서술(B)을 나누고, 결과 계약과 금지 카탈로그를 비교 팔로 둔다. 이 조사의 1차 출처는 바꾸지 않는다.
- 상태: Research note. 채택된 ADR이나 Blueprint 계약이 아니다.
- 목적: “필요 없는 규칙을 삭제하라”는 지시가 실제 삭제 대신 부정문·비활성화로 바뀌는 현상의 원인을, 공개 연구와 관찰 가능한 편집 습관으로 구분한다.

## 조사 질문

1. 이 습관이 특정 제품(Codex, Grok 등)의 버그인가, 여러 모델에 공통인가?
2. 모델이 삭제 지시를 이해하지 못하는가, 이해한 뒤 다른 변환을 선택하는가?
3. 정책 문서의 “규칙을 반대로 고쳐 남김”과 코드의 “가드로 우회해 남김”이 같은 현상인가?
4. 프롬프트만으로 고칠 수 있는가, 학습·평가의 공백인가?

## 비교 기준

- 1차 출처: 측정이 있는 논문과 공개 벤치마크
- 2차 출처: 인간 인지 편향과 말뭉치 통계. 모델 행동의 직접 증거가 아닐 때만 배경으로 사용
- 구분: 관찰(측정된 편집 결과)과 추론(왜 그 결과가 나오는지에 대한 설명)

## 1차 출처

| 출처 | 종류 | 핵심 측정 | 이 조사에서의 역할 |
|---|---|---|---|
| [Ebrahimi et al., 2026. *To Add Is Machine, To Delete Is Human*](https://arxiv.org/abs/2607.28887) | 코드 편집 측정 | SWE-bench Verified 해결 패치에서도 개발자 삭제 재현율 최대 71.7%. 해당 파일은 92% 이상 수정하지만 정확한 줄 삭제는 52% 미만. 통과 패치의 29.0%가 Guard-and-Go | 삭제 대신 우회·잔존이 여러 frontier 모델의 측정된 습관임을 보여 준다 |
| 같은 논문의 CanItDelete | 삭제 전용 벤치마크 | 추가 작업 없이 삭제만 요구해도 최고 모델이 5건 중 1건 실패. “workaround 금지” 문구는 성공률을 −2.5~+2.5pp만 바꿈. 정확한 줄 번호를 주면 미삭제는 거의 사라지지만 초과 삭제·추가가 늘어남 | 의도를 못 읽는 문제가 아니라, 삭제 경계 제어와 삭제 선택 자체가 약함을 보여 준다 |

| [Santagata & De Nobili, 2024. *More is More*](https://arxiv.org/abs/2409.02569) | 통제 실험 | GPT-3.5, Claude 3.5, Llama 3.1 등이 덧셈형 수정을 뺄셈형보다 선호. 예: Llama 3.1 회문 과제에서 글자 추가 97.85% | 코드 밖 일반 과제에서도 같은 방향의 덧셈 편향이 있다 |
| [Zhou et al., 2026. *How Language Models Process Negation*](https://arxiv.org/abs/2605.03052) | 내부 회로 분석 | 부정은 원개념을 지우는 연산이 아니라 “not Y”의 새 표현을 만들어 관련 토큰을 **촉진**한다. 억제는 더 약하다. 후반층 shortcut attention은 원래 긍정 개념을 다시 올린다 | “삭제” 지시가 왜 “주제에 대한 부정문”으로 실현되는지에 대한 기제 설명 |
| [Adams et al., 2021. *People systematically overlook subtractive changes*](https://doi.org/10.1038/s41586-021-03380-y) | 인간 인지 | 사람은 더하는 수정을 빼는 수정보다 체계적으로 선호한다 | 학습 말뭉치의 인간 편향 배경. 모델 고유 원인이 아니다 |

## 관찰

이 저장소의 공개 커밋이 같은 변환의 **출력 형태**를 보여 준다. 대화 세션은 없다. 운영자는 2026-08-21에, 빼라는 지시를 하지 않았을 수 있다고 정정했다. 커밋만으로 요청을 삭제로 읽지 않는다.

```text
이전: GitHub 서비스의 조회나 변경에는 인증된 GitHub CLI(gh)만 사용한다.
1차 결과 (#42 / de5bd09): GitHub 조회와 변경은 연결된 GitHub connector를 우선한다. gh 전용 정책을 강제하지 않는다.
2차 결과 (#43 / 39bf215): GitHub 도구 절 자체를 삭제하고, 게시 규칙만 남긴다.
```

1차 커밋 제목은 정책을 drop한다고 적었지만, `gh` 주제 절은 남고 선호만 connector로 바뀌며 옛 규칙을 부정하는 문장이 추가됐다. 주제는 유지되고 극성만 뒤집힌다. 절 자체 삭제는 다음 커밋에서 일어났다.

Ebrahimi et al.이 코드에서 측정한 우세 대체 전략은 Guard-and-Go다. 개발자가 제거한 로직을 남기고, 새 조건이나 fallback으로 실행만 우회한다. 주된 하위 형태는 *Retained Path as Live Fallback*이다. 추가된 가드가 보고된 사례만 처리하고, 개발자가 지운 경로는 그 외 입력의 기본 경로로 남는다.

같은 논문은 주석 처리나 비활성화를 삭제로 인정하지 않는다. 그 정의에서 보면, 정책 문장의 반전은 코드의 가드·주석 처리와 같은 등급의 실패다. 둘 다 대상이 파일에 남아 있고, 독자는 원래 규칙과 새 우회를 함께 해석해야 한다.

CanItDelete의 diagnostic ladder는 실패 지점을 나눈다.

- 파일 전체와 “삭제만 하라”는 명시가 있어도 미삭제가 다수다.
- “workaround 하지 말라”는 문장은 거의 효과가 없다.
- 정확한 삭제 구간을 주면 미삭제는 크게 줄지만, 경계를 넘기거나 코드를 추가하는 실패가 늘어난다.

저자들은 이를 “삭제 능력이 없다”가 아니라 “삭제를 고르지 못하고 경계를 제어하지 못한다”로 요약한다.

Santagata & De Nobili는 회문, 레고 균형, 요약 개선처럼 코드와 무관한 과제에서도 모델이 빼기보다 더하기를 고른다고 측정한다. 제품 한 곳의 프롬프트 버그로 보기 어렵다.

Zhou et al.은 오픈웨이트 모델이 부정에 내부적으로 반응하면서도, 출력에서는 부정 프롬프트에 긍정 답을 내는 경우가 많다고 측정한다. 후반층 attention을 끄면 부정 정확도가 오른다. 부정 처리의 주된 내부 연산은 억제가 아니라 구성(construction)이다.

## 추론

논문이 측정한 변환은 지시를 못 읽어서가 아니라, 모델이 “없음”을 잘 표현하지 못하기 때문에 생긴다. 이 저장소 #42에 그 해석을 그대로 씌우지는 않는다.

생성은 다음에 올 토큰을 고른다. 없는 문장은 토큰이 없고, “gh를 우선하지 않는다”는 토큰이 있다. 원문과, 확인된 경우에는 사용자 지시가 `gh`를 강하게 활성화한다. Zhou et al.이 측정한 구성 기제라면, 모델은 그 활성화를 지우는 대신 `not prefer gh`에 해당하는 새 표현을 만들고 그것을 문장으로 쓴다. 그 문장은 주제를 다룬 것처럼 보이므로, 지시 이행으로 오인하기 쉽다.

Ebrahimi et al.의 측정은 같은 변환이 코드에서 반복됨을 보여 준다. 이슈를 해결한 패치에서도 정확한 줄을 지우지 않고 가드를 덧붙인다. 기존 테스트는 제거를 검사하지 않아 그런 패치를 통과시킨다. 정책 파일에는 테스트가 더 없다. 반전된 규칙은 “주제를 다뤘다”는 표면 신호를 남기므로, 모델과 느슨한 검토 모두 성공으로 읽기 쉽다.

학습과 평가가 이 선택을 강화한다.

- 사람 글과 코드 말뭉치는 덧셈형 수정을 더 많이 담고, 사람은 실제로 빼기를 잘 놓친다.
- 지시 학습의 전형적인 짝은 “이 문서를 X가 되게 고쳐라”이지 “이 문장을 흔적 없이 없애라”가 아니다.
- 코딩 Agent의 보상은 테스트 통과와 최소 수정에 가깝다. 한 줄을 반대 의미로 바꾸는 편이 블록을 지워 구멍을 만드는 편보다 덜 위험해 보인다.
- `search_replace` 같은 도구는 문자열 치환이 기본 동작이다. 구간 삭제는 더 넓은 문맥 일치가 필요하고, 빈 치환은 실수로 보이기 쉽다.

따라서 Codex와 Grok에서 같이 보이는 이유는 제품 설정 한 줄이 아니라, 공유된 사전학습 분포, 공유된 사후학습 목표, 공유된 평가 공백, 공유된 편집 도구 형태에 가깝다.

프롬프트만으로 고치기 어렵다는 점도 측정과 맞다. CanItDelete에서 명시적 삭제·workaround 금지는 거의 움직이지 않았고, 정확한 줄을 알려 줘야 미삭제가 줄었다. 그 경우에도 모델은 경계를 넘기거나 코드를 추가했다. 삭제는 학습 가능하지만, 현재 기본값은 삭제가 아니다.

정책 파일에서는 한 가지 추가 유인이 있다. 규칙을 지우면 공백이 생기고, 모델은 그 공백을 기본 동작이나 다른 규칙이 채울 수 있다고 본다. 반전 문장은 새 상태를 붙잡아 두는 가짜 계약이다. 원래 규칙이 고장난 connector를 우회하려고 생긴 것처럼, 반전 규칙은 그 우회를 반대 방향으로 다시 쓴다. 이것은 측정이 아니라, 관찰된 치환을 정책 문서에 적용한 해석이다.

## 이 저장소에 대한 함의

- 현상은 특정 Agent 제품의 버그로 취급하지 않는다. 여러 모델의 공통 편집 습관이다.
- 생성 Skill이나 always-on 지침에 “최소화하라”, “관련 없는 것을 지우지 마라”만 두면 치환을 더 쉽게 만들 수 있다. 삭제 요청에는 대상의 부재를 따로 적어야 한다.
- Blueprint나 생성 Skill이 이 문제를 다룬다면, 계약은 구현 형태가 아니라 결과여야 한다. 요청이 삭제면 대상 문장과 그 부정문이 모두 없어야 한다.
- 공식 schema, generator, validator를 지금 추가할 근거는 없다. 필요한 것은 반복 실패의 명명과, 나중에 Pilot할 수 있는 수용 기준이다.
- 이 조사는 Idea 가설의 근거이지 규범 변경이 아니다.

## 한계

- 보고된 AGENTS.md 커밋은 반전 출력의 일화다. 이 저장소가 제품 세션 로그를 재현하지는 않았고, 빼기 지시 여부도 확인되지 않았다.
- 같은 출력 형태는 코딩 Agent 밖 공개 게시물에서도 보인다. 측정이 아니므로 1차 출처로 쓰지 않으며, 목록은 [`docs/idea/subtractive-edit-fidelity.md`](../idea/subtractive-edit-fidelity.md)의 공개 일화 절에 둔다.
- Ebrahimi et al.은 코드 패치를 측정한다. 정책 문장 반전과의 동일성은 구조적 유추이며, 정책 전용 벤치마크는 없다.
- Zhou et al.은 오픈웨이트 소형 모델의 내부 회로다. Codex·Grok 같은 비공개 모델에 같은 헤드가 있다고 단정하지 않는다. 출력 습관이 같은 방향이라는 점만 근거로 쓴다.
- 사후학습 파일럿은 익명 7B 한 규모다. 배포 규모에서 같은 처치가 유지되는지는 저자들도 열어 두었다.
- “최소 수정” Agent 지침이 얼마나 기여하는지는 이 조사가 분리 측정하지 않았다.
