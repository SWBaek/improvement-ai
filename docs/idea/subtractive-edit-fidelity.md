# Subtractive Edit Fidelity

## Status

- State: `Exploring`
- Last reviewed: 2026-08-13
- Next trigger: always-on 한두 문장의 결과 계약이 정책 파일의 반전 잔존을 줄이는지 작은 대조 실험으로 확인한다. 효과가 없거나 초과 삭제가 늘면 Skill·Blueprint로 올리지 않고 Parked 조건을 적는다.

아직 Capability Blueprint, 실행 도구, schema 또는 구현 사양이 아니다. 원인 조사는 [`docs/research/deletion-avoidance-and-rule-inversion.md`](../research/deletion-avoidance-and-rule-inversion.md)에 있다.

## 문제와 배경

범용 코딩 Agent에게 필요 없는 문장, 규칙, 경로를 지우거나 최적화하라고 하면, 대상을 없애기보다 기능하지 않도록 고쳐 남기는 일이 반복된다.

이 저장소에서 공개된 흐름은 다음과 같다.

1. `AGENTS.md`에 “GitHub 조회나 변경에는 인증된 `gh`만 사용한다”는 규칙이 있었다. 당시 GitHub connector가 동작하지 않아 생긴 우회였다.
2. connector가 다시 동작했다.
3. 사람은 그 규칙을 폐기하라고 했다. 즉 해당 구문을 삭제하라고 했다.
4. 1차 결과([#42](https://github.com/SWBaek/improvement-ai/commit/de5bd09958129576ea7717f848b24661d9f4ca95))는 삭제가 아니었다. 같은 절이 “connector를 우선한다. `gh` 전용 정책을 강제하지 않는다”로 남았다.
5. 2차 요청 뒤([#43](https://github.com/SWBaek/improvement-ai/commit/39bf2153f38fe467de0355364fd6737528e2b2fa))에야 GitHub 도구 절이 사라졌다.

같은 형태의 치환은 이 예시만이 아니다. 죽은 코드, 쓰이지 않는 기능, 오래된 주석, 최적화 대상 경로에서도 “없애라”가 “끄거나 반대로 적어 남겨라”가 된다. Codex와 Grok 모두에서 관찰되었다.

핵심 불편은 모델이 게으르다는 인상이 아니다. 사람이 공백을 기대한 자리에, 반대 의미의 새 규칙이 남아 이후 세션의 기본 동작까지 왜곡한다는 점이다.

## 현재 관찰

- 삭제 요청 이후에도 원래 주제(`gh`, GitHub 제어)가 파일에 남는다.
- 남는 형태는 공백이 아니라 극성 반전, 가드, 주석 처리, feature flag, fallback이다.
- 반전된 규칙은 원 규칙을 폐기하지 않는다. 같은 주제를 반대 방향으로 다시 계약한다.
- 공개 코드 편집 측정에서도 통과한 패치가 개발자가 지운 줄을 상당 부분 남기고, 그중 다수가 가드로 우회한다.
- “workaround 하지 말라”는 문구만으로는 측정상 거의 나아지지 않는다.
- 정확한 삭제 구간을 알려 주면 미삭제는 줄지만, 그때는 경계를 넘기거나 코드를 추가하는 실패가 늘어난다.

자세한 출처와 관찰·추론 구분은 조사 note를 따른다.

## 현재 가설

모델은 “없음”을 연산하지 않고, 활성화된 주제를 부정형으로 재구성한다. 그래서 삭제 지시는 주제 삭제로 이어지지 않고, 그 주제에 대한 반대 문장이나 비활성 경로로 실현된다.

가칭 `Subtractive Edit Fidelity`는 해결하려는 편집 결과를 나타낸다. 요청이 폐기·삭제·제거이면, 대상과 그 부정문·비활성 대체물이 모두 없어야 한다. 요청이 동작을 끄되 흔적을 남기라는 것이면 그때만 가드나 반전 문장이 허용된다.

가설의 층은 다음과 같다.

```text
학습 분포와 평가
  덧셈형 수정이 많고, 테스트는 제거를 잘 검사하지 않음
        ↓
내부 부정 연산
  “not Y”를 지움이 아니라 새 표현으로 구성함
        ↓
편집 도구와 Agent 지침
  치환이 기본이고, 최소 수정·비파괴가 보상됨
        ↓
파일에 남는 결과
  삭제 대신 반전, 가드, 주석, fallback
```

이 습관은 특정 제품의 버그라기보다, 여러 모델이 공유하는 편집 기본값으로 보는 편이 맞다. 사전학습 분포 자체는 이 저장소가 고치지 않는다.

전달 형태는 Skill보다 always-on 지침에 가깝다. 트리거가 있는 작업이 아니라, 규칙·문서·코드를 고치는 모든 세션에서 나타나기 때문이다.

탐색 중인 공개 형태는 “`AGENTS.md`에 이 한 줄을 추가하면 삭제 요청이 반전 잔존으로 바뀌는 현상이 사라진다”는 한 줄 계약이다. 이것은 성공 기준이지, 지금 문장을 확정하거나 팁 목록을 만들라는 뜻이 아니다. 코드 벤치마크에서 “workaround 하지 마라”는 거의 효과가 없었고, 부정 지시는 바로 이 실패 모드를 재현할 수 있다. 한 줄이 그 슬로건을 만족하는지부터 재야 한다.

`AGENTS.md` 운영 팁 같은 새 저장소 카테고리는 이 Idea가 만들지 않는다. 카테고리는 검증된 한 줄이 여러 개일 때의 전달 문제이고, 저장소 정책 변경이다. 한 줄이 측정되면 대상 프로젝트의 기존 always-on 파일에 넣는 Blueprint operation이거나 research 결과로 두는 편이, 팁 선반을 먼저 만드는 편보다 작다.

## 기대 효과와 비목표

기대하는 결과는, 사람이 “이 규칙을 폐기해”, “이 경로를 지워”, “이것을 최적화해”라고 했을 때 Agent가 다음을 구분하는 것이다.

- **삭제**: 대상 문장·경로와 그 부정 대체물이 파일에 없다.
- **비활성화**: 사람이 흔적 보존을 명시한 경우에만 가드, flag, 주석이 남는다.
- **반전**: 예전 규칙을 반대로 다시 쓰는 것은 폐기가 아니다. 새 계약이 필요할 때만 별도 문장으로 추가한다.

비목표는 다음과 같다.

- 모델 가중치를 재학습하거나 특정 제품 runtime을 고치는 일
- 모든 최소 수정을 금지하는 일
- 삭제를 강제하는 schema, generator, validator, CI
- 전역 Agent Skill이나 사용자 홈에 편집 습관 교정기를 설치하는 일
- 최적화 요청을 무조건 삭제로 해석하는 일
- 효과 측정 없이 이 저장소 루트 `AGENTS.md`에 편집 습관 문단을 상시 추가하는 일
- 원인 논문을 더 모아 같은 결론을 반복하는 일
- `AGENTS.md` 운영 팁 카테고리나 팁 목록을 먼저 만드는 일
- 측정 전에 “이 한 줄을 넣으면 현상이 사라진다”고 홍보하는 일

## 위험과 반례

- 어떤 변경은 진짜로 반전 계약이 필요하다. “더 이상 `gh`를 강제하지 않는다”를 명시해야 다른 Agent의 기본값이 다시 `gh`만 쓰게 하는 경우가 있을 수 있다. 그때 공백은 의도가 아니다.
- 정확한 줄을 강조하면 초과 삭제가 늘어난다는 측정이 있다. 삭제 충실도를 올리다가 관련 없는 인접 규칙을 지울 수 있다.
- “최소 수정”과 “대상 부재”는 충돌할 수 있다. 한 줄을 반대로 바꾸는 편이 diff는 작아 보인다.
- 정책 문장 반전과 코드 Guard-and-Go를 같은 능력으로 묶는 것은 아직 유추다. 한쪽에만 효과가 있을 수 있다.
- 생성 지침이 길어지면 always-on 예산을 잠식한다. 이 습관을 루트 `AGENTS.md`에 장황히 복제하면 안 된다.

## 검증 기준 또는 실험 질문

1. 삭제 요청 후 원 문장과 그 부정문이 모두 없는가?
2. 같은 요청을 Codex, Grok, 다른 Agent에 반복하면 반전 잔존 비율이 제품보다 과제 유형에 더 의존하는가?
3. “삭제하라. 반대 규칙으로 바꾸지 마라. 대상 주제가 파일에 남아 있으면 실패다”처럼 결과 기준을 적으면 프롬프트만으로 줄어드는가? 조사 note는 비관적이다.
4. 같은 한두 문장을 세션 프롬프트가 아니라 always-on `AGENTS.md`에 두었을 때, 정책 파일의 반전 잔존이 줄어드는가? 코드 CanItDelete의 비관적 결과가 여기에도 그대로인가?
5. 사람이 “폐기”와 “반대 정책을 남겨라”를 구분하면, 지침 없이도 잔존이 줄어드는가?

아직 3–5는 이 저장소에서 측정하지 않았다. 1은 공개 커밋 #42와 #43로만 확인됐다.

## 향후 탐색

- 다음 조사는 문헌이 아니라 작은 대조 실험이다. 같은 삭제 요청을 지침 없음 / 세션 한 줄 / always-on 결과 계약으로 나누어, 원문과 부정 잔존·초과 삭제를 센다.
- 실험 문장은 “반전하지 마라”가 아니라 결과여야 한다. 예: 폐기 요청이면 대상과 그 부정문이 모두 없어야 한다.
- 효과가 있어도 이 저장소 `AGENTS.md`에는 정체성·불변·승인 경계만 둔다는 기존 예산을 깨지 않게, 한 줄 이내로만 검토한다. 대상 프로젝트의 기존 always-on 파일은 별 표면이다.
- 한 줄이 슬로건을 만족하면 그때 전달 형태를 고른다. 기본 후보는 새 카테고리가 아니라, 대상 프로젝트 always-on 파일에 그 문장을 넣는 Blueprint operation 또는 research 결과다.
- 효과가 없거나 초과 삭제가 늘면 Skill, 팁 목록, Blueprint로 올리지 않는다.
- 모델 재학습이나 제품 버그 신고로 범위를 넓히지 않는다.
